## Shared-path conflict resolution

1. **Most specific owner wins.** A broad directory owner does not gain access to a specialist’s file/subtree. Read access and review/sign-off do not imply write access. If a path is unassigned, ask Orchestrator to assign a scoped task before touching it; do not assume ownership.
2. **Claim before editing.** Check `tasks/BOARD.md` and `agents/HANDOFF.md`. All roles may update only their own claims/questions/handoffs. Orchestrator owns task creation, ordering, dependency/status coordination and `tasks/STATUS.md`, but preserves other agents’ claims and handoff text. Never take a claimed task or overwrite another author’s changes.
3. **Cross-owner work goes through the owner.** Append your question/request under your own board entry or Open questions, tag the owning role, and let Orchestrator create/sequence the owning-role task. A shared task must identify the exact files/sections, lead integrator, collaborators, acceptance criteria and required approvals before either agent writes. Permission for one task does not permanently change ownership.
4. **Serialize same-file work.** Section ownership still conflicts at the file level. Agree on the section and edit window in the task, have one integrator apply overlapping patches, and re-read current contents before editing. Stop on an unexpected diff; do not resolve it by deleting another role’s work. Escalate unresolved ownership to Orchestrator; unresolved money/privacy/legal/behavior to the named specialist and human where required.
5. **Specialist boundaries:**
   - `USER_STORIES.md`: UX Researcher owns only research; Product Manager owns stories/acceptance criteria. `METRICS.md` belongs to Data & Analytics, not Product Manager; PM supplies intent by task.
   - `docs/02-design/`: Content Designer owns `VOICE_AND_TONE.md`; Accessibility owns `ACCESSIBILITY.md`; Product Designer owns remaining design docs. In `apps/web/`, Designer owns `src/styles/tokens.*`, Content owns `src/content/*`, Frontend owns the rest. Accessibility changes web code only in a named scoped PR agreed with Frontend and any token/content specialist.
   - `docs/03-architecture/PAYMENTS.md` belongs to Payments. Architect owns remaining architecture documents except the prompts section of `AI.md`, which LLM Engineer owns. ML Engineer sends graph/threshold/eval results to Architect for the non-prompts sections; LLM Engineer records prompt evals in its section. Architect integrates other AI evaluation records. Contract changes require an ADR and Architect approval; Tech Writer submits API corrections rather than editing contracts directly.
   - `packages/shared/` belongs to Architect. Root package manifests/lockfiles/workspace and tooling configuration, `.env.example`, `.gitignore`, and `.github/` configuration belong to SRE. Service owners request root configuration/shared-type changes rather than editing across this boundary. Generated shared types follow the approved API contract, never replace it.
   - Backend owns API ingress; every webhook signature must be verified **before dispatch or any effect**. Payments owns PayPal integration, verification helpers as needed, and payment-specific handlers in `services/api/src/payments/`. The interface is jointly agreed; both sides require duplicate-safe processing and Security review. Neither role can waive verification or authorize a new money flow.
   - Data owns `tests/fixtures/` and `infra/seed/`; QA owns other `tests/`, SRE other `infra/`. QA/ML/LLM request fixture updates from Data, and SRE requests seed changes from Data. Explicit shared tasks are the only exception. Runtime analytics wiring belongs to each service/app owner, with Data supplying event definitions and Architect approving contract/schema changes.
   - `README.md` belongs to Tech Writer. Legal drafts disclaimer language in `COMPLIANCE.md`, requests Tech Writer integration, and reviews the final text. `AGENTS.md` is shared by Tech Writer and Orchestrator only through serialized tasks. Role-file maintenance beyond YT-004 requires a scoped governance task; this bootstrap grant is not ongoing authority. Orchestrator owns this roster; `agents/RULES.md` changes always need human approval.
   - Reviewer owns review comments, not implementation. An agent that authored a change cannot serve as its independent Reviewer; after authoring a fix, hand that PR’s independent review to a different agent.
6. **Behavioral/privacy gates are not optional reviews.** Behavioral Scientist must sign off before merge for notifications, money, drift or social comparison. Content Designer and Behavioral Scientist both approve notification copy. The eight hard rules in `roles/behavioral-scientist.md` and `docs/04-behavioral/ETHICS_CHECKLIST.md` apply to every owner. Q-002 remains synthetic-only pending resolution; a demo requirement cannot override private drift/no visible real-user scores.
7. **Approval is separate from ownership.** Contracts need Architect approval/ADR; main merges, rules, money flow and final demo need human approval. Every PR needs independent Reviewer approval and green CI. Role review, successful local commands, or an orchestrator decision cannot substitute for any of these gates.

## Handoff and completion

Use the `agents/HANDOFF.md` format: Done, Not done, How to verify, Risks / gotchas, Next step. Include concrete artifact paths, actual commands/results, fixture revisions where applicable, and the next named role. Meet task acceptance criteria and the global DoD: applicable passing tests/green CI, updated docs, behavioral checklist, independent review and recorded handoff before DONE. Use BLOCKED or IN REVIEW for unmet gates; do not represent authored scaffolds as tested product behavior.

For this YT-004 bootstrap, return the handoff to the parent Orchestrator rather than editing the board. The parent integrates status, review and any human-gated commit separately.
